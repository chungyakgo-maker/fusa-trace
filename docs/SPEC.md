> 이 문서는 무엇을 만들지 정합니다. 문서별로 어떻게 읽는지는 `docs/FORMATS.md`에 있습니다.
> **개정 2 (2026-11-11)**: `docs/SPEC-REV2.md`(받은 그대로 보관한 개정 기록)를 이 문서에 합쳤습니다. 툴의 정체성이 "관리 툴"에서 "검사기"로 바뀌었고,

> ISO 26262 원문은 저장소에 넣지 않습니다. 조항 번호(2018판)만 인용하고 내용은 요약합니다.

## 1. 목적

> **기능안전 제출 문서를 넣으면, 리뷰 전에 고쳐야 할 추적성·정합성 문제를 알려 주는 검사기.** 입력도 관리도 하지 않는다.

FuSa Trace는 기능안전 제출 문서(FSR, TSC, FMEA, SRS, DIA 등)를 넣으면, 문서 사이의 **추적성 연결이 끊긴 곳**과 **위·아래 요구사항의 값이 어긋난 곳**(ASIL, FTTI, Safe State, 할당, 참조 버전)을 찾아 검사 리포트로 알려 줍니다.

### 왜 필요한가
- 문서(TSC, SRS, FMEA 등)는 ALM(코드비머)과 **따로 작성**한다 → 문서끼리, 문서와 ALM이 어긋날 수 있다
- 고객 리뷰는 **제출 문서**로 받는다 → ALM이 맞아도 문서가 틀리면 지적된다
- 엑셀(DIA·문서)과 ALM은 각자의 원본이다. 이 툴은 **세 번째 원본이 되지 않는다**

### 하는 일
1. **검사 (핵심)**: 검사 규칙(§15)으로 끊긴 연결·어긋난 값을 찾아, 고칠 문서·위치·근거 조항과 함께 보여 주고 검사 리포트 엑셀로 출력
2. **추적성 보기**: FSR → TSR → (FMEA 근거) → SSR/HSR → 시험까지 문서에 적힌 연결을 지도·목록으로 (검사 지적의 근거 확인용)
3. **보조 기능 (유지)**: DIA 기준 산출물 일정·작성 현황, 일정·담당 직접 고치기(v0.7), 내 담당 보기(v0.8), 산출물 작성 리스트 엑셀 — 새 관리 기능은 더 만들지 않음 (2026-11-11 사용자 결정)

### 툴의 원칙

- 데이터 입력 없음. 문서를 넣으면 검사 결과가 나옵니다. (보조 기능의 일정·담당 고치기, 별칭, 예외 사유는 예외)
- 문서의 원본은 엑셀·워드 파일입니다. 툴은 **읽기만** 하고, 문서 내용을 고치거나 요구사항을 만들지 않습니다 (FSR → TSR 자동 생성 없음).
- 같은 문서를 넣으면 **항상 같은 결과** (규칙 기반, AI 판단 없음, 업데이트 확인 말고는 외부 통신 없음).
- 모든 지적에 **어디를 고칠지**(문서·항목·위치)와 **근거 조항**을 붙입니다.
- 연결은 문서에 **적혀 있는 참조**만 사용합니다. 내용을 보고 추측해서 연결하지 않습니다.
- 못 읽은 부분은 숨기지 않고 **"못 읽었음"으로 보여 줍니다.** 틀린 결과를 조용히 보여 주는 것보다 낫습니다.

## 2. 범위

### 1단계에 포함

- 설치형 Windows 앱(오프라인, 개인용)
- 문서 넣기: DIA, FSR, TSC, FMEA, SRS, Verification Report(작성 여부만), 칸 지정으로 HSR·SW 시험 명세
- **검사 결과 화면과 검사 리포트 엑셀** (개정 2, §9.0·§10.0·§15)
- 추적성 화면: 시스템 / 소프트웨어 / 하드웨어 탭, 연결 지도 + 목록
- 산출물 일정 화면(DIA 기준)
- ID 대응표(애매한 연결을 사람이 한 번 고르고 기억)
- 엑셀 출력: 산출물 작성 리스트, 담당자별 요약, 추적성 누락 목록

### 1단계에서 하지 않는 것 (나중)

- 코드비머 연동, 여러 명이 데이터 공유
- 문서 내용 편집, 문서 작성 기능
- Verification Report(동료검토) 체크리스트 내용 읽기 — **작성 여부만** 봄
- SW 유닛·통합 단위 추적, 코드 추적
- 원본 파일에 결과를 다시 써 넣기

### 범위에서 빼는 것 (개정 2)

- Verification Report(동료검토) 체크리스트 내용 → 계속 **작성 여부만**
- 문장 품질 검사(모호한 표현 등)
- 관리용 기능(홈 대시보드, 독촉 문안 등)은 만들지 않음. 산출물 일정·작성 리스트는 지금 기능을 유지하되 보조 기능으로

### 아직 문서가 없는 것 (자리만 둠)

- SSR 문서(SRS), SW 요구사항 시험 명세, HSR, FMEDA: 화면에 칸은 두고 "문서 미등록"으로 표시. 문서가 생기면 넣는 즉시 연결되도록 읽기 규칙/칸 지정 기능을 갖춤.

## 3. 실행 환경과 기술

| 항목 | 결정 |
|---|---|
| 대상 PC | 회사 Windows 10/11 PC, 관리자 권한 없음, 사내 보안 프로그램 있음 |
| 앱 형태 | Electron 설치형 exe (NSIS, **사용자 단위 설치** — 관리자 권한 불필요) |
| 언어 | TypeScript, 화면은 React + Vite (Claude Code가 더 나은 선택이 있으면 제안 후 결정) |
| 엑셀 읽기 | SheetJS(xlsx) — .xlsx와 .xls 모두 읽기 |
| 워드 읽기 | .docx를 zip으로 열어 `word/document.xml`의 표·제목을 직접 파싱 (병합 셀 처리 필요). .doc은 미지원 안내 |
| 엑셀 쓰기 | ExcelJS (서식, 색, 필터, 틀 고정) |
| 저장 | 프로젝트마다 JSON 파일 1개 (`%APPDATA%/FuSaTrace/projects/<id>.json`). 저장은 임시 파일 → 교체 방식으로 깨짐 방지. 네이티브 모듈 없이 가기 위함 |
| 네트워크 | **실행 중 외부 통신은 업데이트 확인·받기(GitHub Release)만.** 원격 폰트·통계 수집 금지. 폰트는 앱에 포함 (업데이트 예외: 2026-11-10 사용자 결정, DECISIONS) |
| 빌드 | GitHub Actions (windows-latest)에서 빌드·테스트 → 설치 파일을 Actions 아티팩트 / Release로 배포 |
| 코드 서명 | 없음 (서명 없는 exe가 회사 PC에서 실행되는지 0단계에서 확인) |

### 보안·기밀

- 저장소는 **퍼블릭**(2026-11-10 변경, `docs/DECISIONS.md` 참고). 그래서 실제 회사 문서는 물론 고객사·제품·회사 이름, 실제 ID도 커밋하지 않음 (자리 표시나 가짜 값 사용).
- 테스트용 문서는 **가짜 데이터로 생성**하되, 실제 문서의 양식 특이점을 그대로 재현 (FORMATS.md §9).
- 사용자는 **보안(DRM) 해제한 파일**을 넣음. DRM 파일이 들어오면 읽지 말고 "보안 해제 후 넣어 주세요" 안내 (판별법: FORMATS.md §1).

## 4. 관리 대상과 연결 구조

```
                    [시스템]                         [소프트웨어]                 [하드웨어]
SG ─▶ FSR ─▶ TSR ──┬─(근거)─ FMEA 고장원인      TSR(S/W) ─▶ SSR ─▶ SW 시험   TSR(H/W) ─▶ HSR ─▶ FMEDA
                   │
                   └ 할당(Allocation)에 따라 S/W 탭, H/W 탭으로 나뉨
```

| 항목 | 정의하는 문서 | 위 단계를 가리키는 칸 |
|---|---|---|
| SG, Safe State | FSR 엑셀 | — |
| FSR | FSR 엑셀 | SG (시트 이름 / FSR 표의 SG 칸) |
| TSR | TSC 워드 | Ref ID (FSR ID) |
| FMEA 고장원인 | FMEA 엑셀 | TSR ID 열 |
| SSR | SRS 워드 | Functional Safety Related (TSR ID) |
| SW 시험 케이스 | (양식 미정) | SSR ID — 문서 생기면 칸 지정 |
| HSR | (양식 미정) | TSR ID — 문서 생기면 칸 지정 |
| 산출물(일정) | DIA 엑셀 | — |
| Verification Report | 파일 존재로만 판단 | — |

## 5. 데이터 모델 (프로젝트 JSON 안의 구성)

필드 이름은 예시이며, Claude Code가 구현하며 다듬어도 됩니다.

**Project**: id, 이름(차종·제어기), 생성일, 오늘 기준일(기본: 실제 오늘)

**SourceDoc** (넣은 문서 1개 = 1 레코드, 버전마다 따로 보관)
- 종류(DIA / FSR / TSC / FMEA / SRS / VR / 기타), 원래 파일명, 정규화 파일명(§FORMATS 8), 문서 안 버전(있으면), 넣은 시각, 파일 해시
- 읽기 결과: 읽은 항목 수, 건너뛴 행과 이유, 경고 목록
- 활성 여부(같은 종류·같은 정규화 이름 중 최신만 활성)

**Item** (추적 대상 1개)
- 종류(SG / SS / FSR / TSR / FMEA_CAUSE / SSR / SWTEST / HSR)
- 적힌 ID 그대로(rawId), 정규화 ID, 제목/요약, ASIL, 할당(HW / SW / BOTH / 외부), 요소(Element), 상태값(문서에 적힌 그대로 + 정규화), 출처 문서
- FSR 전용: 구분(자체 / 타 ECU로부터 / 타 ECU에 요구)
- 중복 표시: 같은 문서 안에 같은 rawId가 여러 번이면 각각 보존하고 `중복 #1, #2`로 구분

**Link** (아래 항목 → 위 항목)
- 출발 항목, **적힌 참조 문자열 그대로**, 해석 결과(대상 항목 또는 없음), 해석 방식(정확 / 정규화 / 끝번호 / 별칭 / 애매 / 없음)

**Alias** (사람이 고른 연결 기억): 문서 종류 + 적힌 참조 문자열 → 대상 항목의 정규화 ID. 문서를 새 버전으로 넣어도 유지.

**Deliverable** (DIA에서 온 산출물 1줄; 한 DIA 행에 파일이 여러 개면 여러 줄)
- DIA 행 번호(No.), Part-clause, 산출물 이름(Work product), 문서 라벨(FMEA, DFA, TSC VR 등), 예상 파일명(Actual work product name 한 줄), 정규화 예상 파일명
- 계획 시작/종료, 실적 시작/종료, 담당(팀, 사람 — 여러 명 가능), 메모(파일명이 아닌 글: "FMEDA 대체" 등)
- VR 여부, 연결된 SourceDoc, VR 작성 수동 체크값(사람이 바꾼 경우)
- 날짜 경고(형식 오류, 종료 < 시작)

**Settings**: 칸 이름 동의어 사전, 사용자가 지정한 읽기 규칙(처음 보는 양식용), 오늘 기준일 덮어쓰기

## 6. 문서 넣기 (공통 흐름)

1. 파일을 끌어다 놓거나 선택 (여러 개 한 번에 가능)
2. DRM 검사 → 걸렸으면 안내 후 중단
3. **문서 종류 자동 판별** (FORMATS.md §2). 판별 실패 시 사용자가 종류 선택 → 필요하면 칸 지정 화면
4. **가져오기 결과 화면** (반영 전 확인)
   - 읽은 항목 수 / 건너뛴 행 수와 이유 / 해석 못 한 값
   - 이전 버전 대비: 추가·삭제·변경된 항목 목록, 항목 수 변화 (예: "TSR 36 → 12 — 양식이 바뀌었을 수 있음" 경고)
   - 문서 안 ID 중복, 형식 오류 목록
5. [반영] 누르면 저장 → 추적성·일정 다시 계산
6. 어떤 단계에서 오류가 나도 앱이 죽지 않고, 오류 내용을 보여 줌

### 문서 ↔ DIA 산출물 연결

- 넣은 파일의 정규화 파일명이 DIA의 정규화 예상 파일명과 같으면 자동 연결 (버전 표기·확장자 무시 → 개정본도 같은 산출물로 연결)
- 같은 게 없으면 비슷한 후보를 보여 주고 사용자가 한 번 고름 → 기억(다음 버전부터 자동)
- 파일명과 문서 종류가 안 맞아 보이면 "확인 필요" 표시

## 7. 연결 해석 (ID 맞추기)

참조 문자열 1개를 아래 순서로 해석합니다 (상세 규칙: FORMATS.md §7).

1. 별칭표에 있으면 그 대상
2. 그대로 일치
3. 정규화 후 일치 (대소문자, `_`/공백/`-` 차이, 앞자리 0 등)
4. **끝 번호 일치**: 같은 종류(TSR 등)의 정의 항목 중 끝 번호가 같은 것. SG 번호가 양쪽에 다 있으면 SG도 같아야 함
   - 후보 1개 → 자동 연결 (표시: "약식 표기")
   - 후보 2개 이상 → **확인 필요** (사람이 ID 대응표에서 고름)
   - 후보 0개 → **없는 ID 참조**

정의 문서 안에서 같은 ID가 여러 번 나오면(ID 중복) 그 ID를 가리키는 참조는 모두 "확인 필요"가 됩니다.

## 8. 상태 정의

### 추적 항목 상태

| 상태 | 조건 | 표시 |
|---|---|---|
| 연결됨 | 다음 단계 항목이 1개 이상 해석됨 | 회색 실선 / 초록 체크 |
| 확인 필요 | 애매한 참조, ID 중복, Yes인데 ID 없음 등 | 노란 점선 / 느낌표 |
| 누락 | 다음 단계가 필요한데 없음 | 주황 점선 끝에 "○○ 없음" |
| 대상 아님 | 다음 단계가 필요 없음 (예: H/W TSR의 SSR, 문서 상태가 미적용/N/A, 타 ECU에 요구하는 FSR) | 회색 글자 |
| 문서 대기 | 다음 단계 문서가 아직 등록 안 됨 | 회색 점선 |

"다음 단계가 필요한지" 규칙:
- FSR(자체, 타 ECU로부터) → TSR 필요. 타 ECU에 요구하는 FSR → TSR 불필요
- TSR → FMEA 근거: 일반(General/공통) 분류는 불필요, 그 외 필요
- TSR(S/W 또는 BOTH) → SSR 필요 / TSR(H/W 또는 BOTH) → HSR 필요
- SSR → SW 시험 필요
- 문서에 미적용·미해당·N/A로 적힌 항목 → 대상 아님(커버리지 계산에서 제외)

### 역방향 확인 (아래에서 위로)

- TSR이 없는 FSR 참조(없는 FSR ID를 가리키는 TSR) → 검사 규칙 C-02
- TSR 연결이 없는 FMEA 고장원인 중 ASIL이 있는 것 → C-08
- TSR 연결이 없는 SSR 중 ASIL(A~D)이 있는 것 → C-07 (`Yes`인데 TSR ID가 없으면 C-09)
- TSR 연결이 없는 HSR → C-11, 검증 대상(SSR)이 없는 SW 시험 → C-12

### 산출물(일정) 상태 — 오늘 기준일로 계산

| 상태 | 조건 (위에서부터 먼저 맞는 것) |
|---|---|
| 완료 | 실적 종료일이 있음 |
| 지연 | 계획 종료일 < 오늘, 실적 종료일 없음 |
| 진행 | 계획 시작일 ≤ 오늘, 또는 연결된 문서가 등록됨, 또는 실적 시작일 있음 |
| 미착수 | 그 외 |
| 일정 미기재 | 계획 일정이 비어 있음 (상태와 별개로 경고 표시) |

### Verification Report 작성 여부

- 자동: DIA에 VR 파일명이 있고 그 파일이 등록되면 O. 또는 파일명에 "Verification Report"와 문서 라벨(TSC, FMEA, FTA, DFA, HSI, HSR, HSD, FMEDA 등)이 들어간 파일이 등록되면 해당 산출물 O
- 수동: 화면에서 O/X 직접 변경 가능(자동값보다 우선, 변경 사실 표시)
- **내용은 읽지 않음**
- DIA에서 VR은 별도 줄(예: "TSC VR", "FMEA VR")로 들어오므로 그 자체로 일정·작성 여부를 관리하고, 같은 문서 라벨의 원본 산출물 줄(예: "TSC")에도 "VR 작성" 칸으로 함께 표시
- VR이 아닌 산출물 중 짝이 되는 VR 줄이 없는 것은 "해당 없음"

## 9. 화면

공통 레이아웃: 왼쪽 메뉴, 위쪽에 프로젝트 이름과 [문서 넣기], [엑셀 출력].

- 메뉴 순서 (개정 2 목표, M8): **검사 결과(기본 화면)** → 추적성 → ID 대응표 → 문서 관리 → 산출물 일정 → 설정
- 지금(v0.9, M6): 검사 결과 → 추적성 → 산출물 일정 → ID 대응표 → 문서 관리 → 설정. 검사 결과 메뉴에 오류 건수 표시. 첫 화면·산출물 일정 위치는 M8에서 바꿈

### 9.0 검사 결과 (개정 2)

- 맨 위: 오류 / 경고 / 참고 건수 카드 (누르면 그 심각도만) + 검사 리포트 [엑셀로 저장]
  - (M8) **"이전 검사 대비: 해결 n건, 새로 생김 m건"**
- 문서별 지적 건수 막대 — "어느 문서를 먼저 고칠지" (오류 많은 순, 누르면 그 문서만)
- 지적 목록 표: 심각도, 규칙 ID·이름, 고칠 문서, 항목 ID, 관련 항목, 내용, 위치, 근거 조항
  - 필터: 심각도, 규칙, 문서
  - 내용 예: "TSR-CTL-SG001-0AA의 FTTI 500ms가 상위 FSR-CUST-0BB의 FTTI 100ms보다 김" (K 규칙, M7)
- 지적의 항목 ID를 누르면 추적성 지도에서 그 항목과 위·아래 연결이 강조되고 상세 패널이 열림 (근거 바로 확인)
- 문서를 넣을 때마다 자동으로 다시 검사 (저장된 결과가 아니라 지금 프로젝트에서 계산)
- 문서가 하나도 없으면 "문서를 넣으면 검사 결과가 나옵니다"
- (M8) **예외 처리**: 지적에 [예외 처리] → **사유 필수** → 목록에서 숨김(필터로 다시 봄)
  - 지적의 지문(규칙 ID + 항목 ID + 관련 항목 ID)으로 기억. 다음 검사에서도 같은 지적이면 유지, 사라지면 자동 정리
  - 예외 처리된 지적은 리포트 시트 3에 사유와 함께 **항상** 나옴
- (M8) **검사 이력**: 검사할 때마다 지적 지문 목록과 건수만 저장 (문서 내용은 저장하지 않음) → 해결/새로 생김 계산과 리포트 요약에만 사용

### 9.1 추적성 (탭: 시스템 / 소프트웨어 / 하드웨어)

- **단계 카드**: 각 단계의 개수와 연결률(%) + 진행 막대. 문서가 없으면 점선 카드에 "문서 미등록"
  - 시스템: FSR 수 → TSR 연결 (n/전체 FSR) → FMEA 근거 (n/대상 TSR) → 시스템 통합 시험(자리)
  - 소프트웨어: S/W 할당 TSR 수 → SSR 연결 → SW 요구사항 시험
  - 하드웨어: H/W 할당 TSR 수 → HSR 연결 → FMEDA
- **연결 지도(기본 보기)**: 단계별 열에 항목을 카드로 놓고 선으로 연결
  - 카드: ID + 짧은 제목 + 상태 아이콘. 상태별 테두리·배경색 (색만으로 구분하지 않고 아이콘/글자 병행)
  - 선: 연결됨 회색 실선, 확인 필요 노란 점선, 누락은 주황 점선 끝에 "TSR 없음" 같은 표시
  - 1:N, N:1 연결 모두 표현. ID 중복이면 같은 ID 카드 2개에 점선이 같이 걸리게
  - 시스템 탭은 SG에서 FSR로 갈라지는 모양
  - **양이 많을 때**(TSR 300개 이상인 문서 있음): SG 선택 드롭다운으로 한 SG씩 보기, 문제 있는 항목 먼저, 정상 연결은 "정상 n개" 묶음 카드로 접었다가 클릭하면 펼침. 화면이 느려지지 않게 할 것
  - 카드 클릭 → 그 항목의 위·아래 연결만 강조 + 옆 패널에 상세(출처 문서, 적힌 참조 문자열 원문, 해석 방식)
- **목록 보기(전환 버튼)**: 표 형태, 상태 필터(전체 / 누락 / 확인 필요 / 연결됨)
- 소프트웨어 탭 아래쪽: **역방향 확인** — TSR 연결 없는 안전 관련 SSR
- 하드웨어 탭: HSR·FMEDA 미등록 상태를 점선 빈 자리로 보여 주고 [HSR 넣기] 버튼. FMEDA 목표값(ASIL별 SPFM/LFM/PMHF)은 참고로 표시

### 9.2 산출물 일정

- DIA에서 온 산출물 목록. 구분(관리 / 시스템 / SW / HW — Part 번호로 자동 분류: 2·8부=관리, 3·4부=시스템, 6부=SW, 5부=HW, 그 외=기타) 묶음
- 칸: 산출물(+ 문서 라벨), 담당(팀·사람), 상태, 계획 시작~종료, 실적, D-day, 등록 문서(버전·등록일 또는 "미등록"), VR 작성 O/X
- 간트 막대: 계획 기간 막대 + 오늘 선 + (있으면) 마일스톤 선. 마일스톤은 프로젝트 설정에서 직접 입력
- 필터: 구분, 담당자, 상태. 지연은 눈에 띄게
- 상단 요약: 전체 / 완료 / 진행 / 지연 / 미착수 / 일정 미기재 건수
- 일정·담당은 **DIA 값을 보여 주고**, [고치기]로 계획·실적 날짜와 담당(팀·사람)을 직접 고칠 수 있음 (2026-11-10 사용자 결정, DECISIONS)
  - 고친 값은 DIA 값과 따로 저장, 고친 칸은 "수정"(아이콘 + 글자)으로 표시, [DIA 값으로]로 되돌림. 상태·D-day·간트는 고친 값으로 다시 계산
  - 새 DIA가 고친 값과 같아지면 수정을 지우고(반영 끝), 다르게 바뀌면 고친 값을 유지하고 "DIA 값이 바뀜" 표시
  - 고친 값은 엑셀 출력의 "DIA 붙여넣기" 시트로 원본 DIA에 옮김 (§10). VR 작성 O/X도 화면에서 수정 가능
- **내 담당** (2026-11-11 사용자 결정): [전체 산출물] / [내 담당] 보기. 내 담당이면 표·상단 요약이 내 것만
  - 내 역할(여러 개): 세이프티 매니저 = Part 2·8(관리) + 그 외 Part(기타), 시스템 = Part 3·4, HW = Part 5, SW = Part 6
  - (선택) 설정의 내 정보와 DIA 담당 칸 비교: 내 이름이 있으면 / 담당 팀이 내 팀이면 내 담당
  - ☆로 산출물을 직접 넣고 뺌 (자동보다 우선, 산출물 키로 기억 → 다음 DIA 버전에도 유지). 줄마다 들어온 이유(자동 · 역할 / 내 이름 / 직접 넣음 / 직접 뺌)
  - 기준이 없을 때 [내 담당]을 누르면 역할 고르기 창

## 15. 검사 규칙 (개정 2)

### 15.1 공통
- 심각도: **오류**(제출 전 반드시 수정) / **경고**(확인 필요) / **참고**(문서 대기 등)
- 문서·항목 상태가 "대상 아님"(미적용·미해당·N/A)인 항목은 검사하지 않음
- 아래 단계 문서가 **아직 등록되지 않았으면** 그 단계 규칙은 항목마다 지적하지 않고, 프로젝트당 참고 1건만 냄
  - 예: "SRS 미등록 — SSR 연결 검사 생략"
- 지적 하나 = 규칙 ID + 대상 항목 + 관련 항목 + 내용 + 고칠 문서 + 위치 + 근거 조항
- 지문 = 규칙 ID + 항목 ID + 관련 항목 ID (+ 같은 ID가 여러 번이면 몇 번째인지). 같은 지문은 한 번만
- 같은 문서를 넣으면 항상 같은 순서: 심각도 → 고칠 문서 → 항목 ID → 규칙 ID
- **근거 조항은 ISO 26262:2018 조항 번호만** 적음. 사용자가 보유한 표준으로 한 번 대조할 것 (개정 2 §10)

### 15.4 규칙별 세부 판단 (M7)

**K-01 ASIL**
- 순서: QM < A < B < C < D
- 값 정리: `B`, `ASIL B`, `ASIL-B` → B / `B(D)` → 분해 표기 (본 등급 B, 원래 등급 D)
- 상위가 여러 개면 가장 높은 상위 등급과 비교
- 하위가 분해 표기 `X(Y)`이면: Y ≥ 상위 등급이면 통과(대신 K-05 대상), 아니면 오류
- 하위 값이 비었거나 `-`면 K-01은 건너뛰고 참고 "ASIL 미기재"

**K-02 FTTI**
- 읽을 값 예: `500ms`, `500 ms`, `2500ms`, `100`, `FTTI: 100ms`
- `500ms / 250ms`처럼 여러 값 → 가장 큰 값으로 비교
- `-`, `N/A`, `T.B.D.` → 건너뜀 (`T.B.D.`는 참고 "FTTI 미정")
- 상위가 여러 개면 가장 짧은 상위 FTTI와 비교
- 상위 FTTI는 FSR 값이 없으면 SG의 FTTI 사용

**K-03 Safe State**
- ID 추출: `SS001`, `SS_001`, `SS-001`, `<코드>SS101` 등 → 같은 형태로 정규화
- 하위 값에 SS ID가 하나도 없고 `N/A`·`-`도 아니면 (예: `Normal Mode`, `S N/A`) → "Safe State 형식 아님" 경고
- 하위 SS ID가 상위 FSR(없으면 SG)의 SS ID 집합에 없으면 → 경고
- 상위가 `-`이거나 미정이면 건너뜀

**K-05 DFA**
- 다음 중 하나라도 있으면 "DFA 등록됨"
  - DIA에서 DFA 라벨 또는 Dependent failures 산출물에 연결된 문서
  - 등록 문서 파일명에 `DFA` 토큰
- 분해 표기가 있지만 상태가 "대상 아님"인 항목뿐이면 검사하지 않음

**K-06 참조 버전**
- TSC에서 읽기: `상위문서` 표의 문서번호 칸, 참조 문서 표의 FSR 파일명·버전 → 버전 토큰(`R2.0`, `R00`, `V1.5`, `v1.5`) 추출
- SRS에서 읽기: 참조 문서 표의 `Baseline Version` 칸 중 TSC(또는 System Requirement) 행
- FSR 최신 버전: 개정이력 마지막 버전, 없으면 파일명의 버전 토큰
- 버전 비교 전 정리: `R2.0` = `R2` = `2.0`, `R00` = `R0` = `0`, 대소문자 무시
- 참조 칸이 `TBD`이거나 비어 있으면 → 참고 "참조 버전 미기재"

### 15.5 테스트용 가짜 문서 (FORMATS §9에 체크리스트)

규칙마다 **걸려야 하는 경우와 걸리면 안 되는 경우**를 최소 1개씩 넣습니다.

- C 규칙(M6): FORMATS §9 "검사 규칙용"
- K-01: 상위 B → 하위 A(오류), 상위 D → 하위 `B(D)`(통과 + K-05), 상위 D → 하위 `B(C)`(오류), 상위 여러 개
- K-02: `500ms` vs `100ms`(오류), `500ms / 250ms`, `100`(단위 없음), `T.B.D.`(참고), FSR 값 없음 → SG 값 사용
- K-03: `Normal Mode`, `S N/A`(형식 아님), `SS_001` vs `SS001`(같음), 상위에 없는 SS ID
- K-04: Allocation 빈칸, 해석 불가 값, 괄호 오타 `S/W (CUST))`(정상으로 해석)
- K-05: 분해 표기 + DFA 미등록(경고), 분해 표기 + DIA의 DFA 산출물 등록(통과)
- K-06: TSC 상위문서 `TBD`(참고), `R1.9` vs 최신 `R2.0`(경고), SRS `Baseline Version` 불일치
- 예외 처리(M8): 다음 버전 문서에서도 같은 지적 → 유지 / 고쳐져서 사라짐 → 자동 정리
- 검사 이력(M8): R1 → R2로 바꿨을 때 해결·새로 생김 건수가 정확함
